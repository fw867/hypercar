# 连接诊断

更新：2026-11-02。先确定最后一个已完成阶段，再判断哪些代码实际执行过。

| 已有证据 | 可得结论 | 下一步记录 |
|---|---|---|
| 已配对 / 加入车机 Wi-Fi | 系统保存配对或已入网 | 当前车机端 CarPlay 激活、服务注册结果 |
| 主监听与控制服务 ready | 手机本地准备完成 | 车机 ACL / SDP / RFCOMM、控制邀请 |
| 车机发起 RFCOMM | 进入本轮蓝牙传输 | Detect、SYN、认证、识别与凭据 |
| 收到控制邀请 | 车机开始推进 AirPlay | 本轮端点、Network、配对验证 |
| SETUP / RECORD 成功 | 控制协商和媒体启动已推进 | 实际画面、音频、后续关闭通道 |
| TCP EOF / abort | 对应通道关闭 | 发起方、HCI 原因、其他通道与时间顺序 |

车机立即显示“检查移动设备蓝牙和 Wi-Fi”，不能仅根据界面文字判定 Socket 绑定错误。若尚无 iAP2 或控制邀请，后续媒体 Socket 和通信状态回应通常还未执行，不能直接归因给这些代码。

HCI 中手机发起 HFP 与车机发起 iAP2 是不同流程；HFP 被拒绝不等于捕获到 CarPlay 的 RFCOMM 尝试。没有车机发起 ACL 也不能证明车机没有做任何 Wi-Fi 活动。

## 身份与服务

分别核对系统配对、真实蓝牙 MAC、控制 TXT id、持久 AirPlay 控制身份、接收端配对资料。不要把系统界面显示的地址差异直接当成车机拒绝根因。服务日志必须区分 registering 与 registered，以及回调是否属于当前代次。

`SETUP 403` 需要结合接收端、档案、身份和本轮激活检查，不能统一解释为某一证书错误。不把互删设备、清空身份、关闭 IPv6 或反复切换系统蓝牙作为默认修复步骤。

## 时间与日志

两份应用导出可能重叠，按完整行和时间去重。区分当前会话序号、控制/事件通道及 CSeq；主动停止与异常 EOF 分开统计。事件接近只说明相关，不能直接推出因果。

优先保留 `SESSION-CLOSE`、`NET-WATCH`、`NETEND`、`MARKER` 及握手日志；配合[采集说明](CAPTURE.md)。已经确认的时间线与未完成验证见[验证记录](VALIDATION.md)。
