### 新找到的具体实现差异：资源与视频流生命周期

CatPlay `CarManager::flush_modes`：

- 本地取得主屏且尚无流：先排队声明最新 modes，再创建屏幕流。
- 车机取得主屏且已有流：释放屏幕 guard，清理该流 TEARDOWN，并同步模式。
- `requestUI` 尝试以 UserInitiated 取得主屏、标记模式待反馈，回普通 200。
  没有另一个“桌面已启动”私有确认；没有把 changeUIContext 当作强制夺屏命令。

HyperCar 当前在 `airplay.rs:400` 无条件 `screen_session.open/install`，
即使 `/info` 初始化主屏仍为 2/2；`screen.rs:280` 通过所有权门控暂停媒体。
第一次合法 2→1 的 requestUI 会回报归属并补关键帧，继续使用预先建好的流。
正常 1→2 时也不清除流；实验重建主要由重复 requestUI 或缺失流的恢复意图触发，
不是每次画面资源交接时执行 CatPlay 的同一生命周期。

这是一项真实流程差异，但不是这次才引入的回归：旧媒体实现同样提前建立视频流。
526 曾成功，今天第一次 requestUI 后也已送出视频，后续重建仍失败，
所以只能列为兼容性实验候选，不能写成已找到必需缺失流程。
与其继续提高重复 requestUI 的重建频率，更值得单独测试：在保持原默认路径的前提下，
让一个可选模式将初建/释放/重建严格绑定主屏归属，不动音频、不绕过 Never 约束。
如果实现，应检查资源 revision、旧 sender 先释放、模式反馈与新流提交顺序，
并测试在 SETUP 等待期间车机重新借屏的取消路径。

### 邀请差异的准确边界

CatPlay 的正常客户端在收到 ctrl 邀请后创建 transmitter。
`cp_ctrl_server.rs` 也有特殊分支：发现的 AirPlay 服务缺少 CARPLAY_CONTROL 能力时，
允许每会话一次自邀请；此外提供显式 force_invite 入口。
因此不能概括成“CatPlay 绝不主动连接”，也不能说当前主动 Wi-Fi 一定违反其全部路径。
上述传统设备分支有明确条件，并非凭任意已配对热点上的开放端口判定界面已授权。
本次 /info features 含 bit 37（CatPlay 的 CARPLAY_CONTROL），但第一轮未收到 mDNS 服务记录，
不能将 /info 值冒充 CatPlay 实际判断使用的 Bonjour 记录。

当前无邀请时 10 秒主动连接成功后，退出等待端点循环；该循环原会调用
`advertiser.ensureForNetwork`，包含 30 秒无邀请有限刷新。
进入媒体阶段后 accept 线程和 NSD 注册仍存在，晚到邀请仍能被接收，
但代码没有一个“主动媒体已建立、等到了晚到邀请后再校准界面激活”的专用状态。
不能把停止调用有限刷新说成“广播消失”或“晚到邀请一定被丢弃”；
今天也没有晚到邀请，无法验证该路径是否需要重建或只需更新状态。

## 550：画面资源联动实验与旧实验移除

按用户授权开始实现后，用户进一步要求删除今天无效的两项旧恢复实验。
最终删除设置入口、引擎配置字段、重复 requestUI 让出/取回报文、重复点击强制重建及其专属状态和测试。
旧的 `ui_retake_recovery` / `screen_stream_recovery` 偏好不再读取；不会自动启用新实验。

设置 → 连接与唤醒新增“画面资源联动（实验）”，默认关闭，下次连接生效。
关闭时沿用原先提前建立屏幕流、用所有权门控暂停媒体的流程。
开启时使用如下独立生命周期：

1. 全局 RECORD 和资源声明完成前不创建屏幕流；未取得主屏时继续控制、音频与保活。
2. 最新有效画面归属允许手机使用后，先完成 modesChanged 反馈，再 SETUP、打开视频 socket、
   安装发送器并请求新配置和关键帧。全局 RECORD 沿用会话原结果，不随视频交接重复发送。
3. 车机收回主屏，停止旧发送器，确认 socket 已释放，再发仅 type 110 的 TEARDOWN。
   音频流、控制连接、媒体来源保持独立；归还后重新派生连接、密钥和初始 nonce。
4. 串行工作器在每次网络等待后复核画面 revision。SETUP 途中借屏会撤销过期发送器并清理部分流；
   排队安装也由实际视频泵再次检查授权。即使快速借屏又归还，旧发送器也不会凭 owner=true 恢复旧授权。
5. 相同授权下重复 requestUI 只反馈并请求关键帧，不反复重建。
   SETUP/视频写出失败保留音频和控制，后续合法资源/UI 事件可重试；Never 约束仍生效。
6. 主动停止时按当时已协商的流构造 TEARDOWN；尚未建立或已释放的视频不会作为活动视频写入退出列表。

诊断增加 SESSION-ORIGIN（是否收到真实 ctrl 邀请、端点来源、本轮蓝牙状态、已知网络），
初始接收端屏幕约束、每次 requestUI 前的归属、事件应用后的 revision、
资源反馈应答与 SETUP/安装/撤销/释放顺序。等待状态显示“等待主屏使用权”，不显示视频通道已就绪。

## 对 Gemini 四项判断的验证

结论：资源/HMI 激活可以继续作为假设，但给出的消息方向、当前握手状态和补发方案不能直接采用。
本节重新读取当前源码、今日原始日志、CatPlay 固定版本及 Apple/Android 公开一手资料，未修改运行代码。

### 首先修正故障前提

今日可以确认 AirPlay verify、SETUP、会话内 /info、RECORD 和音频建立；
五轮 Wi-Fi iAP2 均为 WAIT_PEER / WAIT_PEER_LONG，未收到首包。
因此不能称为“Wi-Fi iAP2 已成功但 HMI 未解禁”，更不能跳过这个差别推断某项认证后动作缺失。
当前 Wi-Fi iAP2 在控制/事件通道的 iAPSendMessage 内承载，不是另开一条可直接补发命令的任意 TCP iAP2 会话。
用户问题还包括“手动点击无法进入”，与仅“不自动切入”的正常体验策略不同。

### 1. 蓝牙与车机 HMI：部分有依据，宝马具体因果未证实

Apple WWDC17《Developing Wireless CarPlay Systems》公开描述了两种不同恢复路径：

- 点火后的常规重连由车机确认设备支持、建立蓝牙 iAP2、等待无线 CarPlay 可用通知，
  发现设备后通过 CarPlay Control API 发起连接。
- 用户短暂离开、手机变得不可达时，车机可先通过 CarPlay Control API 快速重连；失败才回退蓝牙重连。

因此不能说所有恢复都必须重走蓝牙，也不能把当前“手机无邀请主动打开 AirPlay”
等同于规范描述的“车机通过 Control API 快速重连”。真实邀请的意义仍需保留。
Apple 还要求恢复上次使用的原车界面或 CarPlay；不自动跳转不单独构成故障，但手动无法进入仍需排查。
没有找到公开一手证据确认 Gemini 所说的 MGU-55 内部 Joynext/Harman HMI 标记、
BluetoothCarPlay 扩展或单条 StartWirelessCarPlay 就能解锁前台的具体机制。

当前 app 没有砍掉蓝牙监听。BMW 档案是被动接受 RFCOMM，已有会话按既定顺序发送
CarPlayAvailability 0x4300 和传输标识；主动 Wi-Fi 与监听并存。
“ACL 一连就主动 RFCOMM 快握手”会改变 BMW 主被动角色策略，不能当作已验证的小补丁。
孤立发送所谓 StartWirelessCarPlay 还缺少确切消息 ID、方向和链路/识别状态前置。

### 2. 角色与控制命令：存在方向错误

当前资源约定及 CatPlay EntityEnum：Controller=1 对应手机内容源，Accessory=2 对应车机。
Gemini 把 Controller 解释成原车机，角色反了。
CatPlay 的 CommandType::direction 明确标记 changeModes / requestUI 为 FromAccessory，
modesChanged 为 FromDevice。当前实现是在手机端仲裁后用 modesChanged 报告真实归属，
而非在首帧后向车机反发 changeModes 抢自己的资源。
takeConstraint / borrowConstraint 表达后续资源转移约束，不是一个可任意填入的“强制前台”按钮。

车机→手机的 requestUI 与手机→车机的现有返回原车 UI 请求也不能因名称相同就视为可逆开关。
CatPlay 没有“发送端首 IDR 后等待 200ms，再反发 requestUI 即进入 CarPlay”的通用流程。
当前返回原车 UI 的出站行为也不构成用同一消息进入 CarPlay 的证据。
没有确定根 UI URL 或真实交互样本，不把“不带 URL/根 UI 标识”作为已知有效参数。

### 3. 配置/IDR 竞争：通用排查合理，今日持续故障不符合该解释

项目已经在 sender 安装时请求新关键帧；自绘通过 CarUiCaster/SpikeCaster 调用
MediaCodec.PARAMETER_KEY_REQUEST_SYNC_FRAME，CarWith 则通过自己的重置命令补关键帧。
今日自绘 10:57:53.622 已写配置，53.624 写出 IDR；CarWith 11:02:23.669 起也有配置及关键帧。
两种来源随后持续写视频，并有对端 TCP 内核确认。
所以不能继续用“静态桌面不产帧或首个 SPS/PPS/IDR 没到”解释整个无法进入阶段。
没有找到“所有宝马收到可解码 IDR 前绝对不切屏”的公开一手依据；缺视频可导致问题，
但不能将其写成已经证明的本车 HMI 条件。

### 4. 多网络路由：风险成立，当前实现和记录已有针对证据

`HyperCarRepo.openTcpFd` 在 connect 前对本轮 SessionSocketLease.Network 调用 Network.bindSocket；
Rust 屏幕 dataPort 也经该 SocketProvider 获取 FD。UDP 同样固定网络。
Android 官方说明 bindSocket 后该 socket 流量使用指定 Network，不依赖进程级默认绑定。
不能把 SO_BINDTODEVICE 当成 Android Network 绑定的等价替代。
今日视频 dataPort=6030 已建立且确认了数 MB 数据，现有证据不支持“视频 socket 实际跑到 5G”作为主解释。
这不排除瞬时 Wi-Fi 波动，但不能据此再次笼统改路由。

### 本次处理决定

保持 550 的资源联动实验与定向诊断，不增加 IDR 后 200ms 的反向 requestUI/changeModes，
不改变 BMW RFCOMM 拨号方向、不重置已验证的身份、不重复实现已有关键帧请求和网络绑定。
优先实测真实车机邀请与手机主动恢复的差异；550 的屏幕生命周期是否改善显示仍待实车。

## 对“旧会话等待 120–300 秒、不再邀请”判断的验证

结论：旧业务会话残留是可检验假设；目前没有车机端计时器、旧会话句柄或重试抓包，
不能把等待几分钟定性为固定 120–300 秒的 TCP/DPD 超时，也不能二选一后声称 100% 找到原因。
只开蓝牙的实验可以隔离变量，但不具有排除车机休眠、发现/EIR、设备选择策略、服务注册和链路错误的能力。

### 已有清理及当日日志反证

手动停止已经调用 nativeStopGracefully：停媒体后发送流 TEARDOWN，再关闭控制连接。
今日 10:58:40.665、11:01:48.170、11:02:59.556 均记录 TEARDOWN 200。
后续依然没有新邀请，故“只因为我们完全没发过 TEARDOWN”不符合本次记录。
这些是流退出与控制关闭，并非获得车机整个 HMI 业务状态释放的确认；旧状态残留仍未被排除。
自然失联时 TCP 可能已经不可用，无法保证事后还能发送 TEARDOWN；
把每次蓝牙 ACL/HFP/A2DP 断开都当作下车并拆 Wi-Fi 会话会误伤正常无线交接。
Apple 的公开流程本来允许 Wi-Fi 接管后关闭蓝牙，并支持短暂离车后先走 CarPlay Control API 快速恢复。

今日多次出现新监听注册：10:55:57.531、11:02:06.629、11:03:40.932、11:04:31.805。
不能由此证明车机 SDP 缓存正确，但也不能直接断言始终卡在手机同一个旧 accept 上。
注册就绪日志是本地事实；是否发生远端 SDP/RFCOMM 请求、拒绝、重试，仍需 HCI 证据。

### ServerSocket 与会话 Socket 必须分开

Iap2Bluetooth.dropCurrentSession 已关闭 sessionSocket、pendingDial、activeChannel、currentSocket；
runSession.finally 也关闭会话资源。主 RecoveringListener 则保留可用的 ServerSocket，
accept IOException 时关闭失效监听并在 1 秒后重注册；旧 generation 不能覆盖新监听。
Android 官方明确允许为了接收后续连接保留 BluetoothServerSocket。
关闭它还会撤销 SDP 记录，重注册会自动分配可用 RFCOMM 通道。
因此“每次 ACL 断开必须关闭 ServerSocket，重连 300ms 后重建”不是平台要求，
也没有本车 HCI 证据支持这些固定延时。
fetchUuidsWithSdp 是手机查询远端设备服务，不保证反向刷新车机缓存中的手机服务。

### 核查发现的真实代码边界（尚未修改）

HyperCarRepo 的 ACL 断开处理有两个保留媒体分支：

- Wi-Fi iAP2 与反馈就绪时调用 retireForWifi，后者设置 handoff 并关闭当前 RFCOMM。
- 已知 Wi-Fi 且本轮仍有网络/会话时直接返回，继续媒体，未显式调用 endCurrentSession。

Iap2Coordinator.notifyBluetoothLost 虽已定义，但当前没有调用点。
因此第二条分支存在需要验证的半开会话边界：若平台未使旧 RFCOMM 读循环及时退出，
sessionActive/sessionProductive 可能保持，后续同车新入站会被“已有有效会话”策略拒绝。
这只是从代码推导的条件性风险；今天没有新建 RFCOMM 会话的记录，不能拿它直接解释今天五轮故障。
如果完善这一点，范围应是确认目标设备 ACL 已断开后清理其已建立/待拨 RFCOMM，
保留主 SDP 监听和健康 Wi-Fi 媒体，并处理迟到 ACL 事件与新会话之间的竞争。
不应顺带修改宝马主被动角色或无条件结束 AirPlay。

### 无线抢先与资源参数的错误

## 551：ACL 清理边界与手动停止后的自动连接休眠

用户要求：开启自动连接时手动停止，不再马上恢复自动流程；至少休眠约 10 分钟。该要求替代此前“自动模式下手动停止立即恢复监听”的行为。

| 情况 | 当前会话 | 后续自动行为 |
| --- | --- | --- |
| 自动连接开启，手动停止 | 优雅拆除 | 停止 RFCOMM 监听、Wi-Fi 自动恢复检查、重试、待机保活与闲置音乐监听；10 分钟后恢复 |
| 自动连接关闭，手动停止 | 优雅拆除 | 保持停止，仍可手动启动 |
| 休眠中手动启动 | 立即按正常手动流程建链 | 不取消原休眠期限；其间不会自动重试；到期只恢复允许的自动能力 |
| 休眠中关闭再开启自动连接 | 保留当前手动会话（如有） | 保留原休眠截止时间，不通过开关绕过 |
| 休眠中重启 App | 无旧会话可保留 | 读取持久化期限，继续休眠 |
| 蓝牙 ACL 退出而 Wi-Fi 接管有效 | 保留 Wi-Fi 媒体与控制链路 | 仅关闭捕获的旧对端 RFCOMM，不撤 SDP |

实现：

- `AutomaticConnectionPause` 保存启动次数、单调时钟截止时间及墙上时钟截止时间。同一次开机内按单调时钟计时，修改系统日期不会提前结束；重启系统后退回墙上时钟判断。
- 连接总入口二次检查自动权限；ACL、增强发现、已知 Wi-Fi 回调、重试和前台服务入口同样阻断休眠期间的自动启动。暂停的是自动连接策略，用户设置仍为开启。
- 进程内协程与非精确的 `ELAPSED_REALTIME_WAKEUP` 闹钟负责到期恢复；闹钟回调再次检查期限。系统省电可能延后唤醒，不承诺精确到秒；不增加精确闹钟权限。强行停止后的恢复仍遵循 Android 对强停应用的限制。
- ACL 回调先捕获匹配 MAC 的 socket 引用，再在 IO 协程关闭；CAS 保证排队清理不会关闭替代引用。`sessionActive` 仍由原会话线程 finally 释放，不强行清零。SDP listener 和健康 Wi-Fi 不随 ACL 断开重建。
- 额外给排队的非手动断开增加连接轮次校验，旧 ACL 清理不会拆除已切换的新会话。这里只防止应用内排队工作的过期执行，不声称能辨认所有系统层迟到广播。
