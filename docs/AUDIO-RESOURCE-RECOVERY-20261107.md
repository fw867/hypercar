# 播放恢复时重新申请音频资源

依据 `hypercar-log-20261107-175436.txt`：下午 CarWith 会话中，17:26:12 车机 take 音频后，audio=2/2，后续媒体队列仍有数据但 RTP 发包一直为 0。屏幕归还没有归还音频，持续 PCM 也没有触发资源恢复。

## 本次行为

- 主动点击自绘音乐卡片播放，或当前媒体会话从暂停/停止经过缓冲恢复播放时，排队一次用户级音频资源申请。
- CarWith/CarLife 新媒体流初始化仅作普通级申请；TTS 和持续 PCM 不触发申请。没有通知使用权或音乐 App 不报告播放状态时，CarWith 的用户级恢复触发可能无法到达，仍需采集现场日志。
- 首次发现已播放的会话、播放中重新缓冲，不视为新的用户播放操作。等待队列有上限，超过两秒的旧意图丢弃，普通请求不会继承过期操作的用户优先级。
- 申请遵守车机 take / unborrow 限制；禁用音频或已持有资源时不发新声明。仅 RTSP 200 且业务响应未拒绝后才提交本地归属并打开 RTP 门控；超时、拒绝、非法响应均不开放。
- 等待应答时收到新的资源事件会使候选声明过期，即使对端迟到成功，也不能覆盖新状态。提交只改变音频，不改变屏幕和画面重建策略。
- 音频速率日志新增 `owner_phone`、累计 `blocked_samples`；这两个字段与源幅度、实际 RTP 发包数配合判断无声原因。

沿用既有 modesChanged 声明机制，不直接取消 AudioOut 的所有权检查。对端接受声明不代表扬声器已出声，仍需实车验证。持续播放期间若车机后来接管，不会因每包 PCM 自动抢回；可暂停再播放触发恢复流程。
