# 视频、触摸与画面资源

更新：2026-11-16。音频独立见[AUDIO](AUDIO.md)。

## 所有档案统一绝对会话URI（2026-11-16）

按用户最新要求，URI策略从BMW对照扩展到所有档案，已移除车型开关及配置门控。配对重连选定最终控制连接后无条件生成`rtsp://<authority>/<随机u64会话ID>`，无显式端口；IPv6使用方括号和原始socket scope的URI编码。会话SETUP、屏幕SETUP、RECORD、各类TEARDOWN复用一次绑定的URI，新的控制会话分配新ID。音频SETUP已有地址以及auth/info/command/feedback路径不变，正文/头部/超时/顺序与前一版相同。DiPlay通过不等同于已查明ID9、奔驰或Wi-Fi主动重连黑屏的根因。

## 所有档案默认HEVC优先（2026-11-16）

未保存编码偏好时默认HEVC优先，显式H.264选择保留，非法旧值按H.264处理。启动引擎前枚举手机硬件HEVC Main/Surface编码器，无匹配项时有效请求为H.264；实际编码器仍须通过本轮尺寸/帧率及配置/启动检查。所有车机档案使用相同编码优先策略，包括ID9与MBUX兼容档案，保留各自其它能力、认证、音频和启动顺序。

这里以本轮会话SETUP返回的enabledFeatures/hevc作为接收端明确允许的证据，不从未知/info数值位或车型名猜测HEVC。未明确启用就使用H.264。HEVC会话SETUP收到400/406/415/451/456/461时，仅移除HEVC重试一次；401/403、超时或已接受但正文损坏不以此重试。重试返回实际提议状态，防止未提议HEVC却因接收端意外回显而启用。各车型实车互操作仍需独立验证。

## CarWith 硬件转码和触摸（2026-11-22 更新）

用源 SPS 的宽高比与本轮 `/info` 主屏比较。所有车机档案的CarWith会话中，相对源比例的偏差超过3%，或主屏任一边超过2560像素时，硬解后用GPU拉伸至车机上报的主屏尺寸，再按本轮协商的格式硬编码。主屏不超过2560且比例接近时保留源尺寸。CarWith源端请求和硬件转码器都使用App设置的目标帧率（30或60 fps）。H.264会话中，1920×720及2560×744到2736×800都尝试重编码；源端画布仍受2560×2560约束。若用户优先HEVC且车机明确接受，H.264源仍须编码为HEVC。触摸从车机显示区域逐轴换算到CarWith回复的源坐标，输出编码尺寸不参与第二次缩放。自绘源不启用这套CarWith转码。编码器不支持尺寸或运行失败时仍沿用既有原流回退，不保证每台手机都能成功输出超宽原生尺寸。

车主确认 BMW MGU-55 按实际像素居中显示较小的透传画面。主屏 2736×800、实际输出 2560×744 时，画面起点为 (88,28)，车机触点 (176,283) 对应源坐标 (88,255)。若实际输出已硬件拉伸至 2736×800，画面起点回到 (0,0)，整屏触点再按两个轴映射至 CarWith 输入尺寸。车机上报的全屏安全区本身不能用来判断透传画面的留边。

初始化、编解码和释放均在后台，按硬件加速、尺寸和帧率能力选择命名codec，不使用软件编码器。新旧实例共享生命周期信号量。解码器保留完整参考链，输出画面按目标帧率送入GPU/编码器；输入突发有32包及8MiB稳态/16MiB初始化上限，完整IDR可淘汰未提交旧帧，无法安全续接时等待并请求源IDR。输出队列最多8包/16MiB。硬件异常或持续无输出时，本源轮锁定回退H.264透传，等待SPS/PPS/IDR并保持屏幕加密nonce连续；源重建才重新尝试HEVC。静止页恢复获得新的异步输出期限。

盒子libzjcarlife的sendCmdVideoEncoderInit（样本地址0xfa838）发送0x18007，含width/height/frameRate。手机CarLife会解析这些值，但默认可映射到自己的分辨率档位；实测请求2400×1080、返回1920×1080。手机端 FeatureConfigManager 将 DISABLE_RESOLUTION_OPTION=1 传给 Recorder.useVehicleResolution。HyperCar 在回复功能清单时，若已收到本轮屏幕声明或命中同车画布缓存，就请求按车机尺寸编码。随后 0x18007 取当时最新尺寸，按比例限在 2560×2560 内并对齐偶数。未命中时保留默认选档；0x10008 和源 SPS 用于核对实际结果。libzlink_cp_video_resize是CarPlay resize证据，不能套给CarWith。

DiPlay验证和局限见[验证记录](VALIDATION.md)。BMW ID8.5仍为主线；ID9现在也服从上面的能力门控，不再无条件禁止HEVC声明。

## 尺寸与配置

优先 /info 的 widthPixels/heightPixels，兼容旧 width/height；缺少有效数据时使用设置兜底（默认1920×1080）。自绘编码沿用实际画布、偶数对齐和用户帧率，不固定所有宝马为2732×794。viewAreas/安全区域用于布局和同源坐标换算，不直接缩小整幅画布。

CarWith 实际画布受其本机编码器和2560×2560边界约束。VideoConfig 优先 SPS 可见尺寸，源实际尺寸与触摸空间保持对应；不能仅改头部尺寸宣称真实画面已拉伸。旧 carwith_stretch 偏好不覆盖实际编码尺寸。

来源 AU、向 socket 写出的帧、TCP ACK 和车机解码显示不是同一层。config / IDR 日志保留源尺寸、SPS、头部尺寸及实际写出证据，屏幕 opcode 保活不算视频帧。

## 流切换与归属

首帧等待正确配置和 IDR；源重建清除旧轮配置及片段，不把上一轮的 SPS/PPS 当成本轮成功。地图卡片/全屏复用任务，切换编码器和 Surface，避免两个画面源持续争抢。

画面资源联动由用户实验开关或车型字段 useScreenResourceLifecycle 启用（OR，不改用户保存值）；奔驰试验档案强制开启，其它档案保持默认。取得屏幕资源后声明并 SETUP；收回时暂停并释放屏幕流，保留控制、iAP2及音频。等待后重查资源版本，禁止旧回调重装失效端点。屏幕 SETUP 400 时可以保留控制等待后续资源变化，但这不表示400已解决。

已删除的“CarPlay界面恢复”和“视频通道重建”两项旧实验不再提供设置或执行分支，历史过程从 Git 查询。当前画面资源联动不是把旧实验重新启用。

## 诊断与边界

在手机诊断页开启「诊断日志」后再连接，本轮会话 SETUP 才会请求车机提供统计。切换记录开关后，新值在下一轮 SETUP 生效。排查借屏或卡顿时，可以用日志中的单调毫秒和主屏连接号对齐以下记录。

- `screen_keepalive_write` 记录静止页也会发送的屏幕保活及其实际写完间隔。opcode 5 统计体里的 `queuedFramesAvg` 和 `lossAvg` 是兼容占位值。
- `VIDEO-QUEUE` 记录主视频泵输入队列的帧数、字节数、最老帧龄及出队等待时间。`video_write_slow` 和 `video_write_end` 记录一次慢写的起止及 TCP 采样。ACK 表示对端内核已确认数据。
- 主视频输入 FIFO 的上限为 32 帧、16 MiB、300 ms。积压超限时丢弃尚未进入 TCP 写入的队列帧，保留源控制事件，等待实时同步帧后恢复。恢复继续使用当前屏幕 TCP 和加密帧计数。
- `VIDEO-QOS` 记录主屏视频 TCP 设置的 CS4（DSCP 32）及读回值。IPv4 使用 `IP_TOS`，IPv6 使用 `IPV6_TCLASS`。读回表明 socket 已设置，车端无线优先级仍需实车验证。
- `keyframe_request`、`keyframe_source_sync`、`keyframe_sender_sync`、`keyframe_tcp_write` 按连接号和请求编号关联。摘要按组保留最近四次请求。同步帧标注 IDR 或 HEVC CRA，以及来源和 PTS。源帧可以来自缓存，转码器也可以独立生成输出同步帧。
- `VIDEO-FEEDBACK` 仅归属发出请求时的主屏连接。`rfps=0` 表示车机报告零，`rfps=unknown` 表示没有可归属的有效值。车机报告收到视频后，还需要解码和合成才能显示。

PIPELINE 分开显示 RECORD、资源、screen_setup、video_tcp_ready、源数量及已写帧。SETUP 和资源请求记录 CSeq、完整出站 plist/hex/哈希及 RTSP/业务应答。空体400只能证明请求被拒，EOF不能反推拒绝码。旧 TCP 端点一旦失效，先使输出和触摸所有者失效，再关闭 socket；连接号和采样年龄用于避免把旧连接统计当成本轮状态。

保留目前已验证的 nonce、AAD、HKDF及NTP映射；没有证据时不因为别的接收器参数不同就改宝马加密和帧头。测试边界见[验证](VALIDATION.md)，协议见[PROTOCOL](PROTOCOL.md)。
