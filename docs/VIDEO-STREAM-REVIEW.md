# 视频、触摸与音频

更新：2026-11-04。

## 尺寸与帧率

优先读取接收端 /info 的 widthPixels、heightPixels，兼容旧 width、height；无有效尺寸时用手机设置的宽高。编码尺寸仅向下对齐偶数，不再强制限制到 1920×1080 或约 110 万像素。默认 60 FPS，用户选择较低帧率仍有效，设置在下次会话生效。H.264 level 由编码器按尺寸和帧率选择。

2732×794 是特定样本与 WinPlay 历史兜底，不是所有宝马或所有接收端的规格。

viewAreas / 安全区域用于界面布局和坐标换算，不直接缩小整幅编码画布；无效区域回退完整画面。触摸必须沿用对应画面和显示区域的同一坐标转换。

## 编码与切换

### 539：统一阶段摘要与独立视频恢复

诊断页增加“连接阶段”，来自本轮引擎结构化 JNI 快照，每秒刷新；导出日志在阶段变化或每 10 秒
记录 PIPELINE 摘要。分别观察控制 RECORD/资源声明完成、Wi-Fi iAP2 阶段、主屏本地归属、
视频通道状态、来源 AU/成功 TCP 写帧数、音频 SETUP、成功 RTP 写包和非零 PCM 包数。
计数均不能证明车机已经解密、显示或出声。首页文案为“会话已连接”，不改变原有视频小卡尺寸。
快照按引擎 generation 隔离，结束后显示上次会话，旧快照不能覆盖新一轮。

Wi-Fi iAP2 在没有首包时显示 WAIT_PEER，15 秒后为 WAIT_PEER_LONG，每 10 秒记录等待状态。
保持被动，不因此发送 SYN、结束媒体会话或重复配对；收到首包后才开始现有 LINK/识别/认证阶段超时。
协议 READY、发送队列屏障到达与密码学真实性验证仍是不同概念，界面只描述传输就绪。

设置 → 连接与唤醒 → 视频通道重建（实验），默认关闭，下次连接生效，可独立于“CarPlay 界面恢复”测试。
requestUI 本地仲裁接受且已经持有画面时，最多每 10 秒尝试一次屏幕流重建：

1. 视频泵释放旧 ScreenSender/socket 并确认；保留 CarWith/自绘源、音频泵、控制通道与 Wi-Fi iAP2。
2. 仅针对 type=110 和当前 screen UUID 发 TEARDOWN。
3. 新 SETUP 使用新 streamConnectionID，派生新密钥/初始 nonce，打开 dataPort。
4. RECORD 成功后交给视频泵全新 sender，请求新 SPS/PPS/IDR。

每个等待完成后检查画面资源版本；车机有新借用/接管即中止恢复，不发布旧的手机抢屏状态。
相同归属下的重复 requestUI 不使正在执行的恢复失效。第一次 2→1 的正常 claim 保留原流程，
实验重建发生在后续已经持有画面的进入请求。初始 SETUP 与重建共用相同的屏幕流创建代码。

只有开启该实验时才对视频 TCP 写入加 2 秒超时；视频写入/保活失败会释放该 sender，
保留其他通道等待下一次允许的 requestUI。重建失败记录失败阶段，不把控制或音频一并拆除；
真实的控制/事件通道关闭仍结束会话。关闭实验时保留原来的整轮失败处理。

验证：54 项 Rust 测试在 Android arm64 真机通过（1 忽略），151 项 Kotlin 测试通过。
新增模拟车机检查旧 socket 先 EOF、TEARDOWN 不包含音频、SETUP/RECORD 顺序、新密钥 nonce=0 可解密、
同一控制通道仍可发 feedback，以及车机中途借屏后不继续 SETUP。
Kotlin 覆盖首包长时间未到但不失败、随后正常响应 Detect、快照未知归属和非零 PCM 与 RTP 计数分离。
这些是发送端与模拟接收端验证；宝马实车效果仍需验证。

## 音频

Shizuku 下 AudioRecord / REMOTE_SUBMIX 采集系统播放的 PCM16、48kHz、双声道；当前 AirPlay SPF 为 352，约每秒 136.36 包。不把该通路描述成麦克风或电话桥接。

自绘 UI 每 5 秒检查一次采集窗口。只有整窗 PCM 全零、系统媒体正在播放且媒体输出不在
REMOTE_SUBMIX 时，才通过 shell 的 AudioManager 媒体策略将输出暂时选到采集设备，单次采集最多尝试一次。
结束采集时仅在当前偏好仍为本次设置的设备时还原之前的偏好，保留用户或系统后续的路由选择。
状态日志记录路由掩码、媒体活动、静音、音量及恢复结果，不把发包计数当作存在非静音音频的证据。
该机制不处理车机蓝牙连接、不启动麦克风、不修改 CarWith 的采集方式。

2026-11-04 在 Xiaomi M154FF / Android 17 上以测试音复现：显式指定其他媒体输出时，535 版
采集 12 秒持续为零；修复版在约 5 秒后恢复非零 PCM（peak=3864）。这是路由抢占的复现与恢复验证，
不是对当天实车静音唯一原因的证明。系统历史显示 CarWith 的采集设备 18:06:11 已移除，
自绘采集 18:06:50 才开始，不支持这轮存在两套采集同时抢占的判断。

WinPlay / DiPlay 联调中使用 audioLatencyMs=250 配合 128 包队列，已验证出声改善；这不代表宝马应该采用相同延迟，也不能据此推断宝马无声的通用原因。

媒体传输、控制与事件应分别看待；RECORD 成功不代表后续每个通道都健康。网络与关闭行为见[协议](PROTOCOL.md)。
