## 可执行修复方案：两轮分别处理

进一步核对发现，`HyperCarRepo.kt::socketProvider` 实际直接创建 `Socket()`、`DatagramSocket()`，依赖已有的进程网络绑定；并未像 `RustCoreBridge.SocketProvider` 注释要求那样逐 socket 绑定本轮 Network。不能误称当前完全没有网络绑定，也不能认定这一差异已证明导致第一轮 abort。

1. **第一轮先加固网络归属与诊断。** 每代 AirPlay 捕获本轮已确认的车机 Network，控制、事件、视频、UDP socket 在 connect 前显式绑定该 Network；绑定失败不静默转默认网络，失败时关闭尚未移交的 socket。保持 mDNS 所需进程绑定，但媒体 socket 不依赖后续全局默认绑定变化。补充 Network 句柄、接口/地址及 capabilities/linkProperties 变化、丢失与首个 socket 异常的关联记录；排除过期回调影响新会话。显式绑定只解决归属不明确的问题，真实网络消失仍会断，不能承诺单靠这一项修好 103。
2. **第二轮先核验回应字段，再补业务。** 对 AE01、4155、4158、4171、AD01 建立可审查的编码定义，按成功盒子完整字段和可信类型定义逐项复核，检查方向、必选字段、长度及字段组合，避免只比较 ID/包数。补充认证后有限数量的 CSeq/链路 ACK 关联记录。收到导航/目的地订阅后，按能力及实际导航状态处理；无路线时如协议定义允许则发布明确非活动/不支持状态，不编造目的地，不调用现有错误方向的 5200 构造器。A101 保持车辆状态接收语义，不造业务回包。
3. **分别验收。** 网络归属修改与认证后业务修改分开验证，以便分辨效果。保留已成功的 AA06→AA01→AA03、逐帧发送和窗口策略，以及昨晚已改善的车机激活入口。对第一轮以系统/网络异常关联为验收证据，对第二轮以业务序列、持续音视频和交接结果为证据；一次超过 8 秒不等于已覆盖长期稳定性。

Android 官方说明支持逐 socket 绑定网络且要求在连接前执行：[Network.bindSocket](https://developer.android.com/reference/android/net/Network#bindSocket(java.net.Socket))；进程级绑定是另一层机制：[ConnectivityManager.bindProcessToNetwork](https://developer.android.com/reference/android/net/ConnectivityManager#bindProcessToNetwork(android.net.Network))。以上为待实施方案，本轮尚未改运行代码。


## 核验：第一轮是否因晚到 5703 重新连接热点

用户提出“蓝牙 iAP2 后到的热点参数触发重新连接车机 Wi-Fi，导致波动”的假设。原理上值得防范，但本轮日志和调用路径不支持将其认定为已发生事件：

- 10:28:09.426 已绑定已知车机网络；36.606 收到 ctrl 邀请后，端点等待函数返回，关闭该轮端点 Channel。
- 36.607 的端点没有 SSID/密码，`joinAndBind` 走无凭据分支，仅绑定已有网络；36.618 控制 TCP 使用 Network #111 建立，没有静默入网日志。
- 37.938 才从蓝牙收到 5703。其 `onEndpoint` 回调只向上述 Channel `trySend`；接收函数已返回，不再消费。附带的晚到端点逻辑仅记录 AirPlay 地址/端口，不调用 Wi-Fi join。
- 37.938 至 44.969 socket abort 之间，没有“先拿到热点凭据——立即入网”“尝试静默加入热点”或再次 WIFI 绑定记录。

因此，当前最具体结论是：**没有发现 HyperCar 在这次晚到 5703 后执行重新入网，不能用该机制解释此次中断。** 系统或车机自身是否在这段时间发生网络重配置，应用日志仍不能排除；这是另一种假设，需要系统证据。

另有独立的防御改进值得后续保留：`joinAndBind` 的幂等检查依赖 `joinedSsid/joinedNetwork`；若未来改成实时消费晚到凭据，应校验现有 Network 与目标身份/SSID，已连通同车网络时只保存凭据，不重新提交 connect-network。不能为修复本轮未发生的重新入网而增加持续消费回调、反而引入该风险。


## 本轮实施：固定网络 socket 与有限业务校准

按用户要求实施第一轮的网络加固；这消除明确的网络归属缺口，不宣称已经唯一确定或实车修复 os error 103。

- 新增 `SessionSocketLease`，每次 AirPlay 连接捕获确定的 Network。控制 TCP 与交给 Rust 的事件/视频/音频/保活 TCP、UDP 均在 connect 前通过 `Network.bindSocket` 显式绑定；主机名解析及缺省 IPv6 link-local scope 也使用该网络。
- 控制连接保留同一网络上的端口/时机重试，取消失败后轮询其他 Wi-Fi、默认网络及解除本轮绑定的行为。找不到网络时直接明确失败，不让控制与媒体分属不同网络。
- 取消会话或网络丢失使本轮 lease 失效；连接过程中失效的 socket 不再移交 native。绑定/连接/移交失败关闭尚未转交的 socket；成功移交后的所有权保持原有 Rust 路径。
- 协商重试捕获本轮 lease，检查是否仍是当前会话，避免排队的旧重试套用新一轮网络。网络 onLost 仍校验 callback owner，过期回调不能拆新会话。
- 添加 `NET-WATCH`，按网络属性变化记录接口/地址/路由和 validated/internet 状态；仅状态变化时记，不持续刷屏。`NET-END` 在引擎异常时同步保存该网络状态；socket 创建失败包含固定 Network、目标、异常类型。仍需系统日志才能进一步区分系统策略与底层链路异常。
- 晚到 5703 的现有行为保留；本轮未增设实时重新入网路径，未改变蓝牙初配、车机激活门槛、自动/手动控制语义。

第二轮交叉核对 CatPlay 固定版本 `fc52bac7910a07ff3b6d94712175db6013528aa9` 的 `CommunicationsUpdate`，以及本地 Cardeck `503ed37` 的 `VirtualIap2Link.kt`：

- HyperCar 原 4158 用循环写入参数 5～18；两个参考实现均只定义到 17。旧回复还写死一格信号、EmergencyCallsOnly，并声明 telephony/initiate-call 可用，与未接入电话业务的状态不符。
