# CarWith 源端预热与车机转发解耦

用户已指定采用 CarPToCarL 的守候方式，不以“原顺序已验证稳定”为前提。参考 b01e758 的 CarLifeHijack：prewarm 独立守候源端，立即握手、持续接收，RECORD 后 attach 转发。

1. CarLife 七路连接、协议认证、心跳和接收任务由连接尝试持有，不再由一次 AirPlay 媒体引擎持有。先创建该源端服务，再自动拉起 CarWith；不在已连接回调重复拉起。
2. 持续消费源端事件，未附着媒体引擎时只保留有界、短时的当前 GOP、参数集、实际尺寸及音频格式，丢弃历史 PCM。源端重置、编码变化和缓存越界必须丢弃无效 GOP。
3. 媒体引擎附着时按原子顺序得到格式和完整 GOP，再接实时事件；源端通道不随媒体 EOF/内部重试销毁。触摸、请求 IDR、语音及请求尺寸仍使用同一源端实例。
4. 所有权按连接尝试隔离，完整停止/切换释放预热服务，过期清理不得销毁新服务。不改 Wi-Fi 保留/复用规则。
5. 回归验证覆盖缓存边界、重置、原子附着和重试；运行原生/JVM/Lint、构建并保留数据覆盖安装。沿用本批 579/10675，不提交、不推送。实车 EOF 的唯一原因仍需独立证据，不能由本改动宣称解决。
