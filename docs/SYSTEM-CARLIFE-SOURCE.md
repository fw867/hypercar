# 系统 CarLife+ 画面来源

CarLife+ 是新增的第三种来源，独立于自绘 UI 和小米 CarWith。选择来源只在下一轮连接时生效；本轮连接保持开始时的选择。未引入 DeX、额外虚拟屏或其系统控制操作。

## 使用

1. 手机系统需提供 CarLife+ 无线连接功能；HyperCar 本身不包含该系统组件。
2. 在 HyperCar 的画面来源选择「CarLife+」，在手机打开系统 CarLife+ 的无线连接入口，保持等待连接。已识别组件可通过设置中的快捷按钮手动打开；未知 ROM 可自行进入系统页面。
3. 按原有流程连接无线 CarPlay 车机。连接中不自动重开系统页面，以免打断系统的监听和当前会话。

CarLife+ 投屏无需 Shizuku，语音助手默认由手机麦克风收音。

「设置 → 画面与声音 → CarLife+ 车机通话（实验）」默认关闭。开启前在「权限与后台」启动并授权 Shizuku，重新连接后生效。蜂窝通话需要手机支持 Android 系统通话音频接口，并且车机声明双向 `type100 / telephony`。参见 [#124](https://github.com/fw867/hypercar/issues/124) 和[电话音频说明](AUDIO.md)。

实车验证时，先放音乐，再接打蜂窝电话。确认车机扬声器有远端声音、对端能听到车机麦克风，挂断后音乐恢复。日志中的 `phone audio offered` 和 `telephony SETUP ready` 分别表示手机音频端点已交给引擎、车机已接受电话流。

## 实现依据

以 [CarPToCarL 固定版本](https://github.com/jjuugk/CarPToCarL/tree/0e6a061bac00f2ae6a551e40c87cfb3c2a52f91b) 的公开 CarLife 协议与连接流程为主要依据，参考 [PR #111](https://github.com/fw867/hypercar/pull/111) 的来源设置与入口思路；没有整体合并该 PR。

- 系统来源按 CMD 握手先尝试 4.1 加密，再沿用原有的 3.0 明文回退。未确认的 3.0 收到明确版本拒绝（包括 `matchStatus=2`），或已匹配版本但三轮启动仍未出画时，会在新连接试一次 3.2。三轮 3.0 启动失败且从未匹配版本，或未确认的 3.2 命令或首帧失败，会回到 4.1。收到带编码参数的同步帧后保留已确认的明文版本。4.1 路径收到挑战应答或任一轮收到内容密钥交换消息时，继续使用加密模式。
- 3.2 首次启动失败后，若下一轮 4.1 在看到加密握手前结束 CMD 或明确拒绝版本，可再试一次 3.2。3.2 明确拒绝版本，或已经出画的 3.2 连续三轮新 CMD 未能出首帧时，经同样的 4.1 检查重新探测 3.0，重新计算原有的三轮启动预算。仅次通道断开不计入这三轮，新同步帧会清零。
- 由 3.2 触发的恢复探测耗尽后，等待 15 秒再尝试 4.1。若这轮仍在加密握手前失败，允许一次延迟的明文恢复。已出画的 3.2 因连续无首帧回退、且 3.0 也启动失败时，延迟恢复重试 3.2。延迟恢复再次启动失败时，以 15 秒间隔重连当前明文版本。明确版本拒绝可以结束当前候选。
- 恢复期间观察到 CMD 端口拒绝 TCP 连接时，等待 15 秒后按 4.1、3.0、3.2 的顺序重新探测。即使三轮 3.0 都在版本匹配前断开，也会继续尝试 3.2。若短暂重启恰好错过拨号，在恢复耗尽且退避结束后，新收到的 4.1 明确版本拒绝可补一次有限探测。该机会在同一来源中只使用一次，收到新同步画面或观察到新的 TCP 端口拒绝后重置。观察到加密握手信号后，继续沿用原有的 4.1 锁定规则。
- 3.2 按盒子固件发送 `CarLife_1.0.0` 版本检查，并应答 `FOCUS_UI`、`VOICE_MIC` 和 `AUDIO_TRANSMISSION_MODE` 特性请求。收到本机 CarLife+ 的正向准入结果后初始化明文视频，视频和媒体通道沿用系统明文实现。
- 自动模式先连接 CMD，允许手机在协商后才开放 VIDEO。明文通道和加密认证前的次通道可独立重连。加密认证后的次通道关闭会结束整轮，按加密模式重新建立密钥和通道。原有小米 CarWith 按七路齐备的 4.1 流程工作。
- 自动模式的 CMD 握手有绝对时限。每次读取先记录缓冲区中已收齐的认证消息，随后按线上顺序验证和响应。未观察认证时限为 8 秒，已观察认证时限为 30 秒。时限独立于会话锁，RSA 密钥生成和种子解密在锁外执行。成功写出视频 START 后，改为等待 VIDEO 交付带编码参数的首个同步帧，最多 8 秒。超时会回收当前轮次。已确认的协议会沿用，未出画的明文探测会计入试探次数。
- 车机身份优先使用本轮接收端，其次使用选择的目标设备，不取无关的最近配对设备。
- 明文模式的视频重配和视频通道恢复复用当前 CMD；自动加密模式不因车机画布迟到而重启手机源。自动模式每轮退出时回收通道、清除回放缓存和待发输入，再等待下次 CMD 连接。每轮单独协商密钥。触摸与硬键直接进入同一有界队列，避免异步转发积压越过轮次清理。
- 车机输出的音频格式、独立导航/语音能力及混音回退继续由已有输出链路协商。
- 有效车机 GPS 通过现有 iAP2 定位链路转为完整 25 字段 `0x18010`，来源首次就绪后无需等待手机端私有订阅，视频重配期间继续转发。沿用 900 ms 节流、2 秒新鲜度和连接归属校验；无效或断开的定位不会继续发送。
- 语音键按实际模式路由：明文模式沿用 CMD `0x68008` 与长按/租约策略，加密模式复用原有加密 CTRL 硬键，不再由“系统来源”标签强制使用 CMD。旧 CMD 的语音租约不能跨重连生效。麦克风默认使用手机；写出控制包仍不等于识别已开始。
- 诊断打印已安装入口/引擎包的包名和版本，以及 `CARLIFE-PROTOCOL` 的具体模式、切换与拒绝消息 ID；入口包版本不代表实际监听引擎的线上协议版本，不打印挑战应答、密钥或音视频正文。

## 验证边界

本地协议模拟与手机原生测试只能验证消息顺序、缺失通道恢复及回归行为，不能代替三星、荣耀等系统 CarLife+ 引擎和实车验证。PR 作者报告的 WinPlay 通过也不能证明其他车机可用。系统入口、实际画面/音频、方向盘语音键以及断线重连仍需对应 ROM 与实车确认。
