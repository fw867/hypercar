## 0.1.0.418：用户要求对照盒子和 CatPlay 后尝试修复

### 新核验的证据

对照本机保存的两组盒子 `iap2-flow-summary.json`、对应固件反汇编，以及干净的 CatPlay `fc52bac7910a07ff3b6d94712175db6013528aa9` 源码。原始盒子日志已不在本轮下载目录，不能冒称重新读取了完整原始 dump；保存的提取结果明确保留截断标记。

1. 两组成功样本在 1D01 后直接发 1D02、AA00，中间没有独立裸 ACK。1D02 自带确认最新车机序号。417 在这里先发一个 9B 裸 ACK，再发两条业务帧，这是之前仅比较消息 ID 所漏掉的调度差异。
2. CatPlay `core/catplay_iap2_link/src/link_layer.rs::next_transmit` 第 5 步先发送会话载荷并清掉 pending_ack，第 6 步才在没有业务载荷时发裸 ACK；确认优先由业务帧捎带。其裸 ACK 不推进发送序号，与本项目的计数方式一致。
3. 两组盒子首个 AA00 链路长度都是 20B，第二个都是 16B。固件 `0x60a70` 创建 AA00，`0x60a74–0x60a80` 检查配件是否支持 AA06；支持时转到 `0x634b8–0x634c0`，调用 `addPara(0)`，再由 `0x60bd4` 路径入发送队列。AA06 分支 `0x5e600–0x5e658` 重新创建无参数 AA00。结合构造代码，首次空参数 0 的含义与条件现已闭合，不再只是从截断日志猜参数。
4. CatPlay 模拟发送端仍默认直接请求证书，不能宣称它实现了盒子的全部序列号流程。其 CSM 定义明确 AA00 参数 0 为请求证书序列号的 flag；因此按本车能力选择路径，未知/未声明 AA06 的接收端保留直接证书请求。
5. 当前外层 `{type:iAPSendMessage, params:{data:<bytes>}}` 与 CatPlay 命令结构及既有固件调用分析一致，继续保留一帧一个命令。认证后的 AA05、设备问候、订阅回应继续依赖实际证书和挑战响应，不复制 CatPlay 模拟端的固定挑战、UUID 或 MAC。

### 改动

- 只在 reliableTransport/Wi-Fi 路径延后裸 ACK 到本次输出收集之前。上层有业务回应时，使用回应帧的 ACK；没有业务回应、早到订阅、重复帧或发送窗口已满时，仍发送裸 ACK，不丢确认。蓝牙即时 ACK 和保活策略不变。
- 解析本轮 Wi-Fi 1D01 的发送清单；明确声明 AA06 才走带空参数 0 的首次 AA00，收到 AA06 后请求无参数证书。未知或未声明者仍直接请求证书。仍兼容车机直接返回 AA01及迟到 AA06，不重新开始已推进的挑战。
- 没有主动改蓝牙退场、资源仲裁、音视频格式或已知 Wi-Fi 触发入口；不伪造 ACK/READY，不增加零重传链路的猜测性重传。

这些是与成功盒子/参考调度对齐的兼容修正，尚不能宣称裸 ACK 或序列号请求是车机静默的唯一原因。此前 412 的串行号请求发生于旧的合并交付实现，不能拿它证明在逐帧交付且捎带确认后此路径仍无效。
